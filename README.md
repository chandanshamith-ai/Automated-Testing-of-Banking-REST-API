# Banking REST API - Unit & API Testing with pytest

Pair project: select, configure and evaluate an industry-standard testing tool against a
non-trivial REST service.

| Item | Choice |
|---|---|
| **System Under Test** | Authenticated banking REST API (Python 3.12 + FastAPI): accounts, deposit, withdraw, transfers with a fee rule |
| **Testing tool** | **pytest** + pytest-cov (coverage) + pytest-html (report) |
| **Test levels** | Unit tests (service layer) and API tests (HTTP layer via FastAPI TestClient) |
| **CI** | GitHub Actions (`.github/workflows/ci.yml`), uploads reports as artifacts |

## Project layout

```
bank_api/
  service.py        business logic: validation, fee rule, ownership, atomic transfers
  app.py            FastAPI routes, bearer-token auth dependency, uniform JSON errors
tests/
  conftest.py       fixtures: fresh bank/app per test, logged-in users, account factory
  test_unit_service.py   UT-01..UT-36
  test_api_auth.py       API-01..API-10, API-40
  test_api_accounts.py   API-11..API-25, API-37
  test_api_transfers.py  API-26..API-36, API-38, API-39
docs/TEST_CASES.md  formal test case design table (ID, precondition, input, expected, technique)
run_tests.sh / .bat / .ps1   run everything and write reports/ (Linux-Mac / cmd / PowerShell)
pytest.ini  .coveragerc  requirements.txt
```

## Setup and run

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
./run_tests.sh                     # cmd: run_tests.bat    PowerShell: .\run_tests.ps1
```

Run only part of the suite:

```bash
pytest -k "ut25 or ut26"           # specific cases
pytest tests/test_unit_service.py  # unit tests only
pytest -m performance              # speed check only
```

## Reports produced in `reports/`

| File | Contents |
|---|---|
| `report.html` | pass/fail per test, durations, failure details |
| `coverage/index.html` | line and branch coverage, missed lines highlighted |
| `junit.xml` | machine-readable results (CI dashboards) |
| `coverage.xml` | coverage in Cobertura format |

The terminal also prints the 10 slowest tests (`--durations=10`). The build fails if coverage drops below 90% (`.coveragerc`).

## Run the API itself (interactive docs included)

```bash
uvicorn bank_api.app:app --reload
```

Open http://127.0.0.1:8000/docs for Swagger UI (auto-generated by FastAPI), or http://127.0.0.1:8000/redoc.

## API summary

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/health` | no | liveness check |
| POST | `/auth/login` | no | `{username, password}` returns a bearer token (demo users: `alice`/`wonderland123`, `bob`/`builder456`) |
| POST | `/accounts` | yes | open an account, optional `initial_deposit` |
| GET | `/accounts/{id}` | yes | read own account |
| POST | `/accounts/{id}/deposit` | yes | `{amount}` |
| POST | `/accounts/{id}/withdraw` | yes | `{amount}` |
| GET | `/accounts/{id}/transactions` | yes | history |
| POST | `/transfers` | yes | `{from_account_id, to_account_id, amount}` |

Business rules R1-R6 are listed at the top of `docs/TEST_CASES.md`.

## Test design approach

* **Equivalence partitioning and boundary value analysis** on amounts: 0.01, 50,000.00, one cent beyond each, zero, negatives, 3 decimals.
* **Fee boundary:** 1,000.00 (no fee) vs 1,000.01 (fee), plus half-up rounding at 1,001.00 (5.005 becomes 5.01).
* **Decision tables** for transfer outcomes (same account / missing destination / not owner / insufficient funds).
* **State and atomicity checks:** after every failed operation, balances are re-read and compared.
* **Error guessing and security:** booleans as numbers, NaN/Infinity, malformed auth headers, SQL-injection-style login, wrong HTTP method.
* **Concurrency:** 200 parallel deposits must not lose updates.
* **Performance:** 200 sequential API calls inside a time budget.
* **Design choices worth explaining in the viva:** money uses `Decimal` and is serialised as a string (floats cannot represent 0.1 exactly); tests build a fresh app per test so they are order-independent; the FastAPI TestClient calls the app in-process, so the suite is fast and needs no running server.
